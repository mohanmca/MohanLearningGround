1. The host networking model

Linux host networking is easiest to investigate from the top down. Applications bind sockets to local addresses and ports. The kernel chooses a route and egress device. A logical interface such as a bond may then choose one physical NIC to carry the frame. The switch side must agree with the host design, especially when link aggregation is involved.

ApplicationJava, service, UDP socket
Local addressIP owned by a Linux device
BondLogical interface such as bond0
NICPhysical port such as eno1
SwitchAccess port or LACP group

A recurring source of confusion is the difference between a physical interface and the logical interface that owns the IP address. In a bonded setup, the IP address normally belongs to the bond. The member interfaces carry Ethernet frames, but they usually do not carry the application-facing IP address.

eno1 ----\
          +-- bond0 -- IP: 169.91.200.111/25
eno2 ----/
Address note: 169.91.200.111/25 is an ordinary unicast IPv4 address in this example. It is unrelated to multicast merely because a multicast group might look similar, such as 239.91.200.111.

2. Linux bonding basics

Network bonding combines two or more physical network interfaces into one logical interface. RHEL uses this pattern for high availability, aggregate throughput in supported modes, and operational consistency when an application should bind to one stable host address rather than to a specific NIC.

High availabilityIf a NIC, cable, or switch port fails, another member can take over.
Aggregate capacitySome modes can distribute separate flows across multiple links.
Stable host identityThe service IP lives on the bond while physical members can change role.

Physical member interfaces are commonly called bond slaves, bond ports, or bond members. On a server using bond0, applications normally bind to the address assigned to bond0, not to eno1 or eno2.

Common bonding modes

Mode Name Purpose Switch configuration
0balance-rrRound-robin load balancing and aggregationUsually required
1active-backupOne active NIC; another takes over on failureUsually not required
2balance-xorSelects a member using a traffic hashUsually required
3broadcastSends every packet through every memberUsually not required
4802.3ad / LACPStandards-based dynamic link aggregationLACP required
5balance-tlbTransmit load balancingUsually not required
6balance-albTransmit and receive load balancingUsually not required

The most common operational choices are mode 1 for simple failover and mode 4 for redundancy plus higher aggregate bandwidth when the upstream switch supports LACP.

Failure-domain reminder: Bonding protects against a NIC, cable, or switch-port failure. Protection against an entire switch failure requires the two NICs to connect to separate switches that support the selected bonding design.

3. LACP and 802.3ad

LACP, the Link Aggregation Control Protocol, is the standard protocol used by Linux bonding mode 4. It combines multiple physical Ethernet links into one logical link when the host and switch ports are configured as the same aggregation group.

RHEL server                         Network switch
+-------------+                    +--------------+
| eno1 -------+--------------------| Port 1       |
| eno2 -------+--------------------| Port 2       |
|      bond0  |      LACP group    | Port-channel |
+-------------+                    +--------------+
Both sides must agree: LACP must be configured on the RHEL server as an 802.3ad bond and on the switch ports as the same port-channel or LAG. Simply connecting two cables without matching switch configuration can create connectivity problems.

Why use LACP?

  • It provides failover if a NIC, cable, or switch port fails.
  • It combines link capacity across multiple independent traffic flows.
  • It detects whether links are correctly connected and participating.
  • It prevents incorrect links from silently joining the bond.

Two 1 Gbps links may provide up to 2 Gbps of total aggregate capacity. A single TCP connection normally remains on one member link and is still limited to roughly 1 Gbps, because LACP distributes flows by hash rather than splitting one flow packet-by-packet.

Useful LACP settings

Setting Meaning Common value
mode=4Uses IEEE 802.3ad dynamic link aggregationRequired for LACP
lacp_rateControls how often LACP PDUs are exchangedfast for about 1 second; slow for about 30 seconds
xmit_hash_policyChooses which member carries each outgoing flowlayer3+4 is common for IP and port based distribution

For LACP health, /proc/net/bonding/bond0 should identify the mode as IEEE 802.3ad dynamic link aggregation. Members should be up, have compatible speed and duplex, and normally appear in the same aggregator.

cat /proc/net/bonding/bond0
Bonding Mode: IEEE 802.3ad Dynamic link aggregation
LACP rate: fast
Aggregator ID: 1
Actor Churn State: none
Partner Churn State: none
Slave Interface: eno1
MII Status: up
Slave Interface: eno2
MII Status: up

5. Bond health investigation

The live kernel bonding status is exposed under /proc/net/bonding. Each file corresponds to one bond and contains the mode, active member, link monitoring status, speed, duplex, failure counts, and LACP-specific state where applicable.

ls -1 /proc/net/bonding/
cat /proc/net/bonding/bond0
cat /proc/net/bonding/bond1
cat /proc/net/bonding/bond3

Only read files that exist on the host. To summarize every bond without dumping the full file:

for b in /proc/net/bonding/*; do
  [ -e "$b" ] || continue
  echo "== ${b##*/} =="
  grep -E 'Bonding Mode|Primary Slave|Currently Active Slave|MII Status|Slave Interface|Speed|Duplex|Link Failure Count|LACP rate|Aggregator ID|Actor Churn State|Partner Churn State' "$b"
  echo
done
Observation Interpretation
Bond and active slave show MII Status: upPhysical link monitoring currently sees the path as healthy
Currently Active Slave is set in active-backup modeTraffic should be using that member unless the host has unusual policy or offload behavior
Link Failure Count increasesThe link has flapped since the bond was created; compare timestamps and switch logs
Speed or duplex differs between slavesConfiguration, cabling, or switch-port settings may be inconsistent
LACP members have different aggregator IDsMembers may not be in the same switch aggregation group
No files under /proc/net/bondingNo kernel bond is currently registered, or the host uses another mechanism such as a team

Active-backup behavior

Mode active-backup uses one member at a time. The standby takes over when link monitoring declares the active member unhealthy. It provides redundancy, not bandwidth aggregation. Depending on primary and primary_reselect, traffic may or may not return to the preferred NIC after recovery.

Bonding Mode: fault-tolerance (active-backup)
Primary Slave: eno1
Currently Active Slave: eno1
Slave Interface: eno1
MII Status: up
Slave Interface: eno2
MII Status: up
Do not test failover by bringing a production slave down unless the change is approved and an out-of-band recovery path exists. Capture the read-only state first.

6. NetworkManager view

On RHEL 9, NetworkManager is usually the management layer that creates and applies the host's connection profiles. A connection is a saved or active profile. A device is the kernel interface. The names can differ, so always check both.

nmcli connection show
nmcli -t -f NAME,DEVICE connection show --active
nmcli device status
nmcli connection show --active
nmcli -f GENERAL,IP4 device show bond0
Device state Meaning
connectedNetworkManager activated a profile on the device
unmanagedNetworkManager intentionally does not control the device
connected (externally)The device has usable configuration created outside the active NetworkManager workflow; NetworkManager observes it without claiming the original configuration
disconnectedManaged, but no active connection profile is applied

Bond member devices can legitimately have no IP address. The important checks are whether the bond owns the intended IP address, whether the active profile maps to the intended bond device, and whether the slave profiles match the host standard.

7. Routes and unicast baseline

After confirming address ownership and bond health, prove that ordinary unicast works before troubleshooting multicast. The route lookup decides the outgoing device, source address, gateway, and routing table. It performs a lookup; it does not send a packet.

ip -4 route show
ip rule show
ip route get <destination_ip>

Replace <destination_ip> with a real IP address, without angle brackets:

ip route get 169.91.200.112
ip route get 169.91.200.113
ip route get 239.91.200.111

For the example multicast lab, all nodes are on the same /26 subnet and should route through bond0.

Node Address Role
Node A169.91.200.111/26Producer
Node B169.91.200.112/26Consumer
Node C169.91.200.113/26Consumer

Understand the example subnet

The address 169.91.200.111/26 uses the first 26 bits for the network and the remaining 6 bits for hosts. The address is valid because .111 is between the first and last usable addresses.

Item Value
CIDR/26

Block size64 addresses

First usable IP169.91.200.65
Last usable IP169.91.200.126
Broadcast address169.91.200.127
Usable host addresses62
Controlled traffic: ping, ncat, socat, Python producers, and tcpdump are test/observation tools, not passive configuration reads. Coordinate them on production hosts.

Prove unicast before multicast

Run a ping matrix before debugging multicast group delivery. If unicast cannot work between producer and consumer nodes on bond0, multicast will not be reliable.

# From Node A
ping -c 3 169.91.200.112
ping -c 3 169.91.200.113

# From Node B
ping -c 3 169.91.200.111
ping -c 3 169.91.200.113

# From Node C
ping -c 3 169.91.200.111
ping -c 3 169.91.200.112

Inspect neighbor state on each node after route and ping checks:

ip neigh show dev bond0

8. Multicast design and host settings

UDP multicast uses a producer that sends datagrams to a group and one or more consumers that join the group. The network forwards traffic only where receivers are interested, subject to host configuration, firewall policy, IGMP behavior, and switch support.

Setting Example value Why it matters
Multicast group239.91.200.111Private application group from administratively scoped 239.0.0.0/8
UDP port5000Producer and consumers must agree on the port
Interfacebond0Both route selection and group join should use the intended host interface
Producer source169.91.200.111Sets the outgoing interface for explicit multicast sends
Consumers169.91.200.112, 169.91.200.113Each consumer must join the group on its local bond0 address
TTL1Correct for same-subnet multicast; routed multicast needs a separate design
Group versus host address: Do not send multicast traffic to a normal unicast IP such as 169.91.200.112. A unicast destination identifies one host. A multicast destination identifies a group that multiple hosts can join.

Check that bond0 supports multicast

ip -br link show dev bond0
ip -details link show dev bond0
ip -details link show dev bond0 | grep -o MULTICAST

Look for UP, LOWER_UP, MULTICAST, and the expected MTU. If the MULTICAST flag is missing, this is an approved remediation example:

sudo ip link set dev bond0 multicast on
ip -details link show dev bond0

Check the multicast route

Linux normally knows that 224.0.0.0/4 is multicast, but an explicit route can be useful when a host has multiple interfaces.

ip route get 239.91.200.111
ip route show 224.0.0.0/4

If the group routes through the wrong interface, these are remediation examples for an approved change window:

sudo ip route add 224.0.0.0/4 dev bond0
ip route get 239.91.200.111

sudo ip route replace 224.0.0.0/4 dev bond0

To persist the multicast route with NetworkManager, first find the active bond0 connection:

CONN=$(nmcli -t -f NAME,DEVICE connection show --active | awk -F: '$2=="bond0"{print $1; exit}')
echo "$CONN"

Then add the route to the profile and reactivate it during an approved window:

sudo nmcli connection modify "$CONN" +ipv4.routes "224.0.0.0/4"
sudo nmcli connection up "$CONN"
ip route show 224.0.0.0/4

If your NetworkManager version requires a next-hop field, use 0.0.0.0:

sudo nmcli connection modify "$CONN" +ipv4.routes "224.0.0.0/4 0.0.0.0"
sudo nmcli connection up "$CONN"

Check reverse path filtering

Reverse path filtering can drop packets when the return path does not match the receiving interface. It is more common with multihomed hosts, asymmetric routing, or traffic arriving on an interface Linux does not expect.

sysctl net.ipv4.conf.all.rp_filter
sysctl net.ipv4.conf.default.rp_filter
sysctl net.ipv4.conf.bond0.rp_filter

For controlled testing, disable it temporarily or use loose mode only with network/security approval:

sudo sysctl -w net.ipv4.conf.all.rp_filter=0
sudo sysctl -w net.ipv4.conf.default.rp_filter=0
sudo sysctl -w net.ipv4.conf.bond0.rp_filter=0

sudo sysctl -w net.ipv4.conf.bond0.rp_filter=2

Validate firewall rules

On RHEL consumers, the UDP port must be allowed by the active firewall policy. Read the active zones and open ports first:

sudo firewall-cmd --get-active-zones
sudo firewall-cmd --list-ports

Approved examples for opening UDP port 5000:

sudo firewall-cmd --add-port=5000/udp

sudo firewall-cmd --permanent --add-port=5000/udp
sudo firewall-cmd --reload
sudo firewall-cmd --list-ports

sudo firewall-cmd --zone=public --permanent --add-port=5000/udp
sudo firewall-cmd --reload
Do not permanently disable the firewall in production. If a controlled test requires stopping firewalld, restart it immediately and preserve the test evidence.

9. Multicast test producers and consumers

After link, IP, subnet, unicast, route, and firewall checks are clean, test application-level multicast. The important application behaviors are binding a UDP socket, joining the group on the correct local interface IP, and sending through the expected interface.

Python consumer

Create multicast_consumer.py on each consumer node:

#!/usr/bin/env python3
import argparse
import socket


parser = argparse.ArgumentParser(description="UDP multicast consumer")
parser.add_argument("--group", default="239.91.200.111")
parser.add_argument("--port", type=int, default=5000)
parser.add_argument("--iface-ip", required=True, help="Local IP on bond0")
args = parser.parse_args()

sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM, socket.IPPROTO_UDP)
sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)

try:
    sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEPORT, 1)
except (AttributeError, OSError):
    pass

sock.bind(("", args.port))

mreq = socket.inet_aton(args.group) + socket.inet_aton(args.iface_ip)
sock.setsockopt(socket.IPPROTO_IP, socket.IP_ADD_MEMBERSHIP, mreq)

print(f"listening group={args.group} port={args.port} iface_ip={args.iface_ip}")

while True:
    data, addr = sock.recvfrom(65535)
    print(f"from={addr} bytes={len(data)} message={data.decode(errors='replace')}")

Run it on Node B and Node C:

python3 multicast_consumer.py --iface-ip 169.91.200.112
python3 multicast_consumer.py --iface-ip 169.91.200.113

Python producer

Create multicast_producer.py on Node A:

#!/usr/bin/env python3
import argparse
import socket
import struct
import time


parser = argparse.ArgumentParser(description="UDP multicast producer")
parser.add_argument("--group", default="239.91.200.111")
parser.add_argument("--port", type=int, default=5000)
parser.add_argument("--iface-ip", required=True, help="Local IP on bond0")
parser.add_argument("--ttl", type=int, default=1)
parser.add_argument("--interval", type=float, default=1.0)
args = parser.parse_args()

sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM, socket.IPPROTO_UDP)
sock.setsockopt(socket.IPPROTO_IP, socket.IP_MULTICAST_IF, socket.inet_aton(args.iface_ip))
sock.setsockopt(socket.IPPROTO_IP, socket.IP_MULTICAST_TTL, struct.pack("B", args.ttl))

counter = 0
print(f"sending group={args.group} port={args.port} iface_ip={args.iface_ip} ttl={args.ttl}")

while True:
    counter += 1
    message = f"hello multicast {counter} from {args.iface_ip}"
    sock.sendto(message.encode(), (args.group, args.port))
    print(message)
    time.sleep(args.interval)
python3 multicast_producer.py --iface-ip 169.91.200.111

Expected consumer output should show datagrams from Node A:

from=('169.91.200.111', 54321) bytes=42 message=hello multicast 1 from 169.91.200.111
from=('169.91.200.111', 54321) bytes=42 message=hello multicast 2 from 169.91.200.111

Command-line tests with ncat and socat

Use ncat for a simple unicast UDP test. Use socat for multicast because the receiver must explicitly join the group with IP_ADD_MEMBERSHIP.

# On Node B
ncat -u -l 5000

# On Node A
printf 'hello unicast\n' | ncat -u 169.91.200.112 5000
# On Node B
socat -u UDP4-RECVFROM:5000,ip-add-membership=239.91.200.111:169.91.200.112,reuseaddr,fork -

# On Node C
socat -u UDP4-RECVFROM:5000,ip-add-membership=239.91.200.111:169.91.200.113,reuseaddr,fork -
# On Node A
printf 'hello multicast from node A\n' | socat -u - UDP4-DATAGRAM:239.91.200.111:5000,ip-multicast-if=169.91.200.111,ip-multicast-ttl=1

Repeated producer loop:

while true; do
  printf 'hello multicast %s\n' "$(date -Is)"
  sleep 1
done | socat -u - UDP4-DATAGRAM:239.91.200.111:5000,ip-multicast-if=169.91.200.111,ip-multicast-ttl=1

10. Packet proof and troubleshooting flow

Use packet and process evidence to determine where multicast fails. A running process is not proof that multicast is working; prove each layer separately.

Process and socket proof

ps -ef | grep -E 'multicast_producer|multicast_consumer|socat|python' | grep -v grep
pgrep -af 'multicast_producer|multicast_consumer|socat|python'
ss -uapn | grep ':5000'

A consumer may be bound to 0.0.0.0:5000, *:5000, or a specific node IP. Many multicast consumers bind to all local addresses and then join the group on one interface.

Multicast membership proof

ip maddr show dev bond0
ip -s maddr show dev bond0
netstat -g 2>/dev/null || true
cat /proc/net/igmp
ss -uapnmi | grep -E '239.91.200.111|:5000' || true

Look for 239.91.200.111. If the consumer process is running but the group is not present, the app probably did not join the group correctly or joined it on the wrong interface IP.

Producer and consumer packet proof

# On Node A, prove packets leave the producer
sudo tcpdump -ni bond0 "udp and host 239.91.200.111 and port 5000"

# On Node B or Node C, prove packets arrive at the consumer
sudo tcpdump -ni bond0 "udp and host 239.91.200.111 and port 5000"

# Check all visible interfaces if bond0 does not show packets
sudo tcpdump -ni any "udp and host 239.91.200.111 and port 5000"

If packets appear on any but not on bond0, the traffic may be using another interface, VLAN interface, container namespace, or route.

11. UDP sockets and Java ownership

Use ss to inspect kernel sockets. For UDP investigations, it tells you which local addresses and ports are bound and, with sufficient privilege, which process owns each socket.

ss -uapn
ss -uapn | head
sudo ss -uapn

The flags mean -u UDP, -a all sockets, -p process information, and -n numeric addresses and ports.

Output Meaning
0.0.0.0:9000The socket is bound to port 9000 on all local IPv4 addresses; it does not mean the whole internet
169.91.200.111:9000The socket is bound specifically to that local address and port
UNCONNNormal for an unconnected UDP socket; UDP has no TCP-style connection state
users:(("java",pid=1234,fd=87))Java PID 1234 owns the socket through file descriptor 87

Count UDP sockets owned by Java

sudo ss -H -uapn | awk '
  /users:\(\(\"java\"/ {
    if (match($0,/pid=[0-9]+/)) {
      pid=substr($0,RSTART+4,RLENGTH-4)
      count[pid]++
    }
  }
  END {
    printf "%-10s %s\n", "PID", "UDP_SOCKETS"
    for (pid in count) printf "%-10s %d\n", pid, count[pid]
  }'

ps -p <pid> -o pid,user,etimes,cmd --no-headers

Ephemeral port range

sysctl net.ipv4.ip_local_port_range
cat /proc/sys/net/ipv4/ip_local_port_range

When an application binds to port 0, Linux normally selects an available local port from this range. Explicitly bound service ports can be outside it. Port exhaustion investigation should also consider application lifecycle, network namespaces, and socket churn.

12. Complete investigation script

The script below collects the read-only evidence covered in this article. Save it as rhel9-network-investigate.sh, make it executable, and run it. An optional first argument performs a route lookup for a destination IP.

chmod +x rhel9-network-investigate.sh
./rhel9-network-investigate.sh
./rhel9-network-investigate.sh 239.91.200.111
The script records command availability and permission limitations rather than aborting the whole report. Run it with sudo only if the investigation needs process ownership details from ss.
#!/usr/bin/env bash
set -u

DESTINATION_IP="${1:-}"

section() { printf '\n\n==== %s ====\n' "$1"; }

run() {
  printf '\n$'
  printf ' %q' "$@"
  printf '\n'
  "$@" 2>&1 || printf '[command exited with status %d]\n' "$?"
}

have() { command -v "$1" >/dev/null 2>&1; }

printf 'RHEL 9 host networking investigation\n'
printf 'Generated: '; date --iso-8601=seconds
printf 'Host: '; hostname
printf 'Kernel: '; uname -r
printf 'User: '; id
printf 'Safety: read-only inspection; no network state is changed.\n'

section 'IPv4 addresses and links'
if have ip; then
  run ip -br -4 addr
  run ip -br link
  run ip -d link show type bond
else
  printf 'ip command not found\n'
fi

section 'Kernel bonding status'
shopt -s nullglob
bonds=(/proc/net/bonding/*)
if ((${#bonds[@]} == 0)); then
  printf 'No bond status files found under /proc/net/bonding.\n'
else
  for b in "${bonds[@]}"; do
    printf '\n== %s ==\n' "${b##*/}"
    grep -E 'Bonding Mode|Primary Slave|Currently Active Slave|MII Status|Slave Interface|Speed|Duplex|Link Failure Count|LACP rate|Aggregator ID|Actor Churn State|Partner Churn State' "$b" || true
  done
fi
shopt -u nullglob

section 'NetworkManager'
if have nmcli; then
  run nmcli -t -f NAME,DEVICE connection show --active
  run nmcli device status
  run nmcli connection show --active
  while IFS= read -r bond; do
    [ -n "$bond" ] && run nmcli -f GENERAL,IP4 device show "$bond"
  done < <(ls -1 /proc/net/bonding 2>/dev/null || true)
else
  printf 'nmcli not found; NetworkManager may be absent or tools not installed.\n'
fi

section 'Routes, rules, neighbors, and multicast groups'
if have ip; then
  run ip -4 route show
  run ip rule show
  if [ -n "$DESTINATION_IP" ]; then
    run ip route get "$DESTINATION_IP"
  else
    printf 'No destination argument supplied; skipping ip route get.\n'
  fi
  run ip neigh show
  run ip maddr show
  run ip -s maddr show
fi
run cat /proc/net/igmp
if have netstat; then
  run netstat -g
fi

section 'Reverse path filter settings'
if have sysctl; then
  run sysctl net.ipv4.conf.all.rp_filter
  run sysctl net.ipv4.conf.default.rp_filter
  for bond in /proc/net/bonding/*; do
    [ -e "$bond" ] || continue
    run sysctl "net.ipv4.conf.${bond##*/}.rp_filter"
  done
fi

section 'Firewall state'
if have firewall-cmd; then
  run firewall-cmd --get-active-zones
  run firewall-cmd --list-ports
else
  printf 'firewall-cmd not found; firewalld may be absent or tools not installed.\n'
fi

section 'UDP sockets'
if have ss; then
  run ss -uapn
  printf '\nUDP socket rows grouped by process and PID:\n'
  ss -H -uapn 2>/dev/null | awk '
    {
      name="unknown"; pid="-"
      if (match($0,/users:\(\(\"[^\"]+\"/))
        name=substr($0,RSTART+9,RLENGTH-10)
      if (match($0,/pid=[0-9]+/))
        pid=substr($0,RSTART+4,RLENGTH-4)
      count[name SUBSEP pid]++
    }
    END {
      printf "%-24s %-10s %s\n", "PROCESS", "PID", "UDP_SOCKETS"
      for (key in count) {
        split(key,a,SUBSEP)
        printf "%-24s %-10s %d\n", a[1], a[2], count[key]
      }
    }' | sort
else
  printf 'ss not found; install iproute tools through the approved host process.\n'
fi

section 'Local ephemeral port range'
if have sysctl; then
  run sysctl net.ipv4.ip_local_port_range
else
  run cat /proc/sys/net/ipv4/ip_local_port_range
fi

section 'Investigation notes'
printf '%s\n' \
  'UP is not proof of application reachability.' \
  'A healthy bond is not proof that routes, firewall, multicast joins, or switches are correct.' \
  'LACP requires matching host and switch configuration.' \
  'Missing process details in ss usually require elevated privileges.' \
  'Correlate findings with application logs and approved network telemetry.'
